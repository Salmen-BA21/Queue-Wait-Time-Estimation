\section{Introduction}
Sprint 2 expanded the project from a single local pipeline into a platform that can work with several camera sources. At this stage, the backend became responsible for camera onboarding, feed control, and live delivery, so the rest of the application could communicate with it in a more structured way.

\section{Sprint Objectives}
This sprint had four main delivery goals:
\begin{itemize}
    \item make external camera sources usable inside the project,
    \item expose feed management through a predictable API contract,
    \item keep live delivery available through a fallback-aware transport strategy,
    \item preserve feed state and recovery behavior across restarts.
\end{itemize}

These goals are important because this sprint turns the backend into a reusable service layer rather than a one-off processing script.

\section{Implementation}
\subsection{Camera Source Integration}
This part of the sprint focuses on making external cameras usable inside the project. It supports:
\begin{itemize}
    \item handling camera credentials without exposing them in logs,
    \item choosing between TCP and UDP transport depending on the situation,
    \item checking the connection and capturing snapshots,
    \item reconnecting automatically when the stream is interrupted.
\end{itemize}

The source-handling layer routes local files and webcams through one path and live camera streams through another, which keeps the source logic easier to maintain.

\subsection{Authenticated API Access}
Sprint 2 also introduced session-aware access control in the backend API. Managers can only interact with the feeds that belong to their account, while administrators keep the broader management scope needed for account governance. The same identity context is applied to feed listing, feed creation, feed lifecycle actions, stream snapshots, and websocket subscriptions so the runtime respects the ownership rules defined earlier in the report.

\subsection{Camera Discovery and Stream Setup}
The camera discovery step is used to find available cameras automatically and recover their stream information. This avoids hardcoding stream addresses and makes onboarding easier when new IP cameras are added.

In the practical setup, the workstation and the IP camera were connected to the same local network through a router, which made the device reachable for discovery and RTSP validation. The test source used during this stage was a Digital Watchdog IP camera, allowing the connectivity workflow to be validated against a real camera feed.

\subsection{API Layer and Data Contract}
The API layer acts as the bridge between the backend services and the rest of the project. It provides structured inputs and outputs so the frontend can interact with the backend in a predictable way. The main groups of operations are:
\begin{itemize}
    \item feed management, including creation, listing, start, stop, restart, and deletion,
    \item source onboarding, including RTSP checks, snapshots, and camera discovery,
    \item metadata management for establishments and cashiers,
    \item integration and health checks,
    \item live transport support for real-time viewing.
\end{itemize}

\subsection{Live Video Delivery}
To reduce viewing latency while still keeping a fallback path, Sprint 2 introduces a transport system that chooses the most suitable stream mode for each feed \cite{webrtc_w3c,ietf_rfc8830}. The backend tells the frontend whether live viewing is ready, whether WebRTC is available, and which fallback should be used when the higher-quality path cannot start. When WebRTC is available, the backend forwards the browser offer to the media server and returns the response needed to start the stream \cite{mediamtx_docs}. If the feed does not exist, is not running, or the media service cannot answer, the backend reports the condition clearly so the frontend can switch to the fallback view instead of failing silently. The configuration stays flexible through environment settings such as the media URL, control URL, timeout, and feature flag.

\subsection{Runtime Control and Live Events}
Runtime control sits inside the API orchestration layer. It keeps track of feed state, synchronizes persistence, manages the worker lifecycle, and dispatches events to the rest of the system. The live channel publishes updates such as snapshots, feed status changes, metric updates, alert notifications, and system warnings.

For the video surface, the system keeps a shared fallback stream so that viewing does not break when the runtime mode changes.

\subsection{Persistence and Recovery}
The persistence layer stores feed configuration, metadata, video sessions, and archived alerts in SQLite. When the backend starts, it reloads saved feeds and safely resets any stale running sessions so the system begins from a consistent state.

\section{Conclusion}
By the end of Sprint 2, the backend could onboard cameras, manage feed state, and send live updates to the frontend without depending on hardcoded source details. That made the web UI work in Sprint 3 much easier to integrate.

\section{Sprint Retrospective}
This sprint clarified the role of the backend as the integration hub. It now handles camera identity, live transport, recovery, metadata, and state synchronization in one place, which reduces coupling in the rest of the system.

The main lesson is that connectivity is not only about reaching the camera. It is also about preserving a usable application state when streams fail, restart, or need to switch transport modes.
