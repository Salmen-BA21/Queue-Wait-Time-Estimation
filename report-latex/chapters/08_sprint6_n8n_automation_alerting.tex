\section{Introduction}
This sprint connected the queue metrics produced by the backend with n8n, so alerts could be forwarded in a controlled way. The main concern was not only to transmit the payload, but also to keep the process reliable, traceable, and easy to repeat during testing.

This chapter sits at the boundary between analysis and operations, so its role is to preserve the structure of the runtime pipeline while handing alert delivery to a dedicated workflow engine. That separation keeps the perception loop responsive and makes the notification path easier to audit.

\section{Sprint Backlog}
Sprint 6 focused on the automation tasks needed to move alerts from the backend into n8n:
\begin{itemize}
    \item define a stable webhook payload and validate it before dispatch,
    \item add retry-based webhook delivery with logging for failures and successes,
    \item connect runtime threshold detection to alert triggering,
    \item create and configure the Telegram bot and store its API credential in n8n,
    \item configure n8n routing for authorization, cooldown, formatting, and delivery,
    \item prepare test scripts for repeated workflow validation.
\end{itemize}

\section{Implementation}
\subsection{Alert Payload Structure}
The webhook schema is centered on \texttt{QueuePayload}, which keeps the information needed by n8n in one structure. It carries:
\begin{itemize}
    \item source metadata (timestamp, frame, source, feed ID),
    \item queue metrics ($\lambda$, $\mu$, wait time, stability),
    \item alert flags and severity fields.
\end{itemize}
Before anything is sent, the payload is validated so malformed records do not leave the backend.

\subsection{Delivery Reliability}
To reduce the risk of missed notifications, the delivery client uses a timeout, a retry policy, an optional shared-secret header, and logging for both successes and failures. Historical payloads remain in SQLite, which gives the system one place to recover past events if needed.

\subsection{Telegram Bot Setup}
Before the workflow could send operational alerts, a Telegram bot was created and connected to the project as the final notification channel. Its API token was added to n8n as a credential instead of being hardcoded, which kept the workflow portable and prevented secret exposure in the exported JSON. Once the credential was available, the Telegram node could use it after the webhook validation and cooldown checks passed.

\subsection{Alert Dispatch in the Runtime Loop}
Inside the main loop, alert sending is moved to \texttt{AsyncWebhookDispatcher} so the perception pipeline keeps running without waiting on the network. This makes it possible to send periodic metric updates and immediate alerts, while a deduplication window limits repeated notifications for the same situation.

\subsection{n8n Workflow Routing and Telegram Delivery}
The n8n alert workflow follows a simple path:
\begin{itemize}
    \item webhook reception and secret validation,
    \item alert detection and cooldown gating,
    \item alert history archival via backend API,
    \item message formatting and Telegram send node,
    \item explicit acknowledge/reject branches.
\end{itemize}
Keeping the no-alert, alert-suppressed, and alert-delivered branches separate makes the behavior easier to audit later.

\subsection{Workflow Validation}
Workflow validation was supported by PowerShell scripts for single-alert checks, automated execution polling, and multi-feed scenarios. These scripts made it possible to replay webhook submissions and confirm that each branch behaved as expected during sprint verification.

\section{Conclusion}
Sprint 6 turned the analytics output into notifications that could reach the operations side, while still preserving a clear history inside the backend.
