\section{Introduction}
Sprint 2 moved the project from simple counting to queue interpretation. At this stage, the system starts estimating how people arrive, how quickly service is handled, and how long waiting should take. It also decides when the queue is no longer behaving in a stable way.

\section{Sprint Backlog}
The Sprint 2 backlog focused on turning tracking results into usable queue indicators:
\begin{itemize}
    \item estimate queue rates from people tracked inside the queue area,
    \item compute wait time while handling stable and unstable cases,
    \item protect the calculations from empty windows and division-by-zero problems,
    \item provide a clear metric output that later layers can reuse.
\end{itemize}

\section{Implementation}
\subsection{Queue Event Windows and Rate Estimation}
The queue-analysis step uses short time windows to count arrivals and departures. Let $N_a$ and $N_d$ be the number of events observed in windows $T_a$ and $T_d$:
\[
\lambda = \frac{N_a}{T_a}, \qquad \mu = \frac{N_d}{T_d}
\]
From these counts, the system estimates the arrival rate and the service rate. To avoid unstable values at the beginning of a run, the implementation waits until enough events have been observed before returning non-zero rates.

\subsection{Wait-Time Logic and Stability Handling}
The queue is considered stable when arrivals stay below service and service is actually observed:
\[
\texttt{queue\_stable} = (\lambda < \mu) \land (\mu > 0)
\]
When that condition is met, the normal wait-time formula is used. Otherwise, the system falls back to a more conservative estimate based on the current occupancy:
\begin{itemize}
    \item stable queue: $W = \frac{1}{\mu-\lambda}$,
    \item unstable but service observed: fallback $W = \frac{L}{\mu}$, where $L$ is the number of people in the zone.
\end{itemize}
When no service events are observed, the implementation returns a zero fallback so that downstream components do not use an unreliable value.

\subsection{Runtime Contract for Monitoring and Automation}
The final metric output includes:
\begin{itemize}
    \item point estimates ($\lambda$, $\mu$, $W$),
    \item people-in-zone occupancy,
    \item stability flag for safe downstream interpretation.
\end{itemize}
These values are then reused by logs, overlays, webhook payloads, and dashboard events.

\section{Conclusion}
Sprint 2 delivered the analytical core of the project. It transforms queue observations into rates, gives a practical wait-time estimate, and keeps a stability signal for the later parts of the system. That makes the next sprints easier to build and validate.
