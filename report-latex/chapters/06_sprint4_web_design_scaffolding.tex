\chapter{Sprint 4: Web Design and Scaffolding}
\chaptertoc

\section{Introduction}
Sprint 4 established the visual system and page structure for the dashboard. The main deliverable was a frontend scaffold that matched the monitoring workflow before live data wiring was added.

\section{Sprint Backlog}
Sprint 4 backlog focused on design-to-code readiness:
\begin{itemize}
    \item Define a consistent visual design system (colors, typography, spacing, component rules).
    \item Produce complete page layouts for onboarding, monitoring, editing, analytics, and settings.
    \item Scaffold a React + TypeScript frontend project with reusable UI primitives.
    \item Establish routing and layout composition patterns for future live integration.
\end{itemize}

\section{Design}

\subsection{UI and UX Design}
The project design specification defines a ``Terminal Minimal'' style system and a seven-page navigation model. The design language emphasizes:
\begin{itemize}
    \item dark operational surfaces optimized for continuous monitoring,
    \item strong semantic colors for status and alert levels,
    \item card-based information density with consistent spacing and hierarchy,
    \item explicit workflow guidance in setup and zone-editing screens.
\end{itemize}

The designed page set includes landing, dashboard, setup wizard, zone editor, analytics, settings, and heatmap views, which directly informed component boundaries in the frontend implementation.

The frontend scaffold separates page-level views, shared UI, hooks, and API adapters so the dashboard can grow without collapsing into one large component tree:
\begin{itemize}
    \item page layer: route-level views (Dashboard, Analytics, ZoneEditor, Settings, etc.).
    \item component layer: reusable UI and domain panels.
    \item integration hook layer: stateful workflow and data hooks.
    \item API adapter layer: contract mapping and helper utilities.
\end{itemize}

\subsection{Design Rationale}
Sprint 4 was intentionally scoped as a scaffold sprint rather than a feature-complete UI release. The aim was to lock down navigation, component boundaries, and interaction patterns before live data and transport logic arrived in Sprint 5. That sequencing kept the report shorter than the implementation-heavy sprints, but it also reflects the actual distribution of work and the role this sprint played in the overall delivery plan.

\section{Implementation}
Sprint 4 implementation established the frontend technical baseline:
\begin{itemize}
    \item Vite + React + TypeScript project initialization with package-managed workspace configuration.
    \item Tailwind CSS and shadcn/Radix-driven UI composition.
    \item React Router page structure and layout shell integration.
    \item Initial dashboard and setup page scaffolding for subsequent live-data wiring.
\end{itemize}

The tradeoff in this sprint was deliberate: structure and design consistency came before real-time behavior. That made Sprint 5 easier because the route map and component boundaries were already settled.

\section{Conclusion}
Sprint 4 left the app with a clear route and component scaffold that reduced rework when live data arrived in Sprint 5.
