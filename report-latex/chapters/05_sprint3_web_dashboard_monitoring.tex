\section{Introduction}
Sprint 3 implemented the frontend from initial design work through live backend integration. The sprint began by establishing the visual design system and page structure, then connected the interface to backend services and runtime events so the dashboard could respond to live data, transport changes, and feed lifecycle actions.

Completing the design foundation first allowed the integration work to focus on behavioral correctness and reliability rather than redesigning the interface during implementation.

\section{Sprint Objectives and Backlog}
Sprint 3 pursued two parallel tracks: establishing a visual design foundation and then integrating the frontend with live backend services. The design phase established the visual language, page structure, and reusable component abstractions before implementation began. The integration phase connected the interface to backend services, ensuring responsiveness across transport state changes and maintaining operational clarity during feed management and fallback conditions. The sprint backlog organized these objectives into manager-facing user stories and technical implementation tasks.

\section{Design}

\subsection{Visual Design and Interface Architecture}
The design follows a ``Terminal Minimal'' style optimized for sustained monitoring operations. The visual language emphasizes dark operational surfaces to reduce fatigue during extended use, semantic colors for status and alert severity distinction, card-based information organization with consistent hierarchy, and explicit workflow scaffolding in setup and zone-editing contexts.

The interface is organized around seven primary pages: landing, dashboard, setup wizard, zone editor, analytics, settings, and heatmap. This navigation structure was established early as the scope boundary, ensuring that the integration phase could focus on behavior and reliability rather than simultaneous redesign.

\subsection{Dashboard Data Flow and Integration Architecture}
The dashboard operates through a structured data flow that balances real-time responsiveness with operational resilience. Initial access requires authentication; once authenticated, the dashboard issues REST queries for feed configuration and system health, then opens a persistent WebSocket connection to the backend. The WebSocket broadcasts an initial metrics snapshot, followed by continuous feed lifecycle events, metric updates, alerts, and warnings. Feed control actions are sent as REST commands and return as status updates through the WebSocket channel.

This architecture is designed for operational continuity: when live WebSocket events stop arriving, the dashboard automatically switches to periodic polling, ensuring managers retain visibility even during transient network failures. For video playback, WebRTC delivers low-latency streams for IP cameras through the backend, while MJPEG serves local video files. The fallback strategy ensures that authentication failures, WebSocket drops, or WebRTC unavailability do not blind the operator—the interface can still poll metrics and display fallback video streams.

\subsection{Design Rationale}
Prioritizing the design phase as a foundation step proved valuable for the integration work that followed. By settling navigation structure, component boundaries, and interaction patterns before connecting live data and transport logic, the team could focus integration efforts on behavioral correctness and reliability rather than simultaneous redesign. This separation of concerns kept the integration phase tractable and prevented design churn from blocking delivery.

\section{Implementation}

\subsection{Project Setup and Layout Skeleton}
The design specification was translated into an application skeleton. Setup established the application entry point, protected navigation, the dashboard layout, and shared components across all pages.

Page organization followed the operational workflow: onboarding precedes configuration, which precedes supervision. The skeleton was structured as an operational path rather than a disconnected set of screens.

\subsection{Styling and Reusable Interface Rules}
The visual system was defined once and applied consistently. Spacing, typography, surface treatment, and semantic colors were treated as reusable rules rather than per-page decisions. This consistency prevented design drift: components appearing across multiple pages behave as unified product elements rather than restyled instances.

\subsection{API Integration}
A dedicated API layer structures communication with the backend, defining data types consumed by the dashboard and centralizing error handling. This layer serves as the contract boundary: the UI does not depend on backend implementation details, and feed lists, dashboard summaries, and management actions are explicit typed responses.

\subsection{Authentication and Role-Based Navigation}
Sprint 3 integrated authentication and role-based access control into the dashboard. The auth provider clears cached data on session changes; protected routes redirect users based on their assigned role; administrators access the manager administration interface while managers reach the monitoring dashboard. This alignment with backend access rules prevents interface mismatch and ensures users only access appropriate functionality.

Three key screens implement this logic: the manager sign-in screen validates credentials before granting dashboard access, the manager account creation screen allows administrators to register new managers, and the administrator interface provides centralized account governance. These screens are shown in Figures~\ref{fig:sprint3_login_page}, \ref{fig:sprint3_signup_page}, and \ref{fig:sprint3_admin_dashboard}. The practical result is that authentication, account management, and role-based routing remain coherent from the user's perspective: each user type encounters only the appropriate interface for their operational role.

\subsection{Dashboard State Orchestration and Live Update Reliability}
A state orchestration layer coordinates data fetching and backend updates. From received feed data, the dashboard derives operational indicators: online feed count, total people, average wait time, and alert count for visualization.

Live reliability relies on the websocket integration layer with multi-layered resilience:
\begin{itemize}
    \item reconnection delays to prevent backend overload during outages,
    \item heartbeat monitoring for early connection loss detection,
    \item stale data guards to prevent outdated metric display,
    \item fallback polling when live events become unavailable,
    \item batched updates for interface responsiveness.
\end{itemize}

When websocket drops, the dashboard automatically switches to polling, maintaining manager visibility. In a monitoring context, operational continuity outweighs transport purity—the interface must remain informative despite network transients. This strategy preserves monitoring surface availability across degraded or interrupted connections.

\subsection{Live Video Delivery and Transport Selection}
The frontend intelligently selects video transport based on source type and availability: WebRTC for IP cameras when available (providing lower latency), and MJPEG for local MP4 files. Each running feed checks transport readiness and routes accordingly.

For IP camera feeds over WebRTC, the browser creates a receive connection, gathers network information, sends an offer to the backend, and applies the returned response to transition to live playback. Reconnection uses increasing delays to avoid backend flooding. When primary transport fails, the system stops retrying and switches to fallback. For IP feeds losing WebRTC connectivity, MJPEG fallback maintains visibility and operational continuity, ensuring monitoring does not depend on a single transport mechanism.

\subsection{Analytics and Historical Reporting}
The analytics view complements live supervision with historical reporting. It aggregates archived alerts and queue metrics so managers can spot trends and bottlenecks without leaving the dashboard.

Four KPI cards summarize: average wait time, peak queue length, stability score, total alerts. A period selector (hourly, daily, weekly) controls granularity; date filters isolate specific windows. The dashboard visualizes wait and queue trends, ranks top and bottom zones, and breaks down alerts by severity. The view also supports CSV export for external reporting. During early pilots when the archive is empty, the interface uses mock data derived from active feeds so the analytics are still meaningful.

\subsection{Integration Testing}
We tested the dashboard through scenarios: setup flows, live event handling, transport fallback, feed routing, and error handling.

The tests do more than catch regressions—they document what the sprint actually delivers. A rendered screen is not enough; the dashboard had to work correctly when websockets reconnected, routes changed, and fallbacks activated.

\section{Conclusion}
Sprint 3 completed the frontend implementation and integrated it with the backend to create a fully operational dashboard. The design-first approach proved effective: by settling the visual language, page structure, and component boundaries before implementation, the integration phase could focus entirely on behavioral correctness and transport resilience.

The key architectural achievement was the state orchestration layer that unified session state, feed control actions, live metric updates, and multi-layered fallback logic into a coherent operator experience. The dashboard remained usable across network transients by implementing WebSocket reconnection with exponential backoff, stale-data guards, automatic fallback to polling, and transport negotiation—ensuring that monitoring continuity does not depend on any single mechanism. This resilience strategy proved essential for operational deployments where transient failures are inevitable.

By the end of the sprint, the frontend was complete and production-ready for alert automation and comprehensive system validation in Sprint 4.
