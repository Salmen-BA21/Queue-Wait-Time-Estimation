\section{Introduction}
This chapter places the Queue Wait-Time Estimation System in its operational, organizational, and methodological context. After a short introduction, it explains why queue monitoring remains an important problem for service organizations and why an end-to-end technical solution is needed rather than isolated counting tools.

The chapter also defines the baseline used throughout the report: the collaboration context with DataDoIt, the problem formulation, the comparison with existing approaches, the solution scope, and the Scrum-based organization of the work. This level of detail matters because the later technical chapters rely on these assumptions.

\section{Presentation of the Project}

\subsection{Project Context}
Manual queue supervision is often subjective, hard to scale, and dependent on continuous attention. In many environments, teams react only after congestion appears instead of anticipating it early with measurable indicators.

This project addresses that gap by turning camera streams into decision-oriented telemetry. The target output is not limited to occupancy counts, but includes people in zone, arrival rate, service rate, expected wait time, queue stability state, and alert states that can be consumed by monitoring and automation layers.

\subsection{Problem Statement}
Existing operational practices and basic counting tools present recurring limitations:
\begin{itemize}
    \item they provide limited anticipation of congestion,
    \item they rarely estimate waiting time explicitly,
    \item they provide weak visibility into queue stability during sudden demand spikes,
    \item they are often disconnected from automated response workflows.
\end{itemize}

As a consequence, interventions (staff reallocation, lane opening, escalation) can be delayed or triggered on incomplete signals. The problem is therefore both analytical and integration-related: it is not enough to produce robust indicators; they also need to be delivered through actionable channels.

\subsection{Study of Existing Approaches}
Recent computer-vision frameworks provide strong building blocks for person perception, notably YOLO-based detection and tracking algorithms such as ByteTrack \cite{ultralytics_docs,bytetrack2022}. Queueing theory, in parallel, offers formal models for service-system behavior, including interpretable relationships between arrival rate, service rate, and expected waiting time \cite{gross_queueing}.

In practice, many deployments remain incomplete. Some focus only on counting and ignore identity continuity; others provide visualization without defining stability clearly; and others stop at analytics without connecting to alert delivery. The result is often a set of disconnected tools instead of one coherent architecture.

\subsection{Proposed Solution}
The proposed system combines perception, analytics, and integration in one modular pipeline:
\begin{enumerate}
    \item person detection and multi-object tracking from camera feeds,
    \item polygon-based queue-zone filtering,
    \item estimation of $\lambda$, $\mu$, and expected wait time,
    \item stable/unstable queue-state interpretation for safe operational decisions,
    \item real-time web supervision through tiered live transport (WebRTC primary, MJPEG fallback),
    \item automation through n8n webhooks and Telegram alerts.
\end{enumerate}

This architecture aims to convert visual observations into operational actions while keeping each layer independently testable. Detection and tracking modules can evolve without rewriting queue formulas, and the web and automation channels can evolve without changing the core metric contract.

\subsection{Objectives of the Project}
The project objectives are to:
\begin{enumerate}
    \item detect and track people in real time,
    \item count people in configurable queue zones,
    \item estimate arrival and service rates,
    \item compute expected wait time,
    \item classify queue stability for operational reliability,
    \item expose metrics through web interfaces and automation workflows.
\end{enumerate}

\subsection{Project Scope and Boundaries}
The implementation scope covers backend perception and analytics modules, API/runtime integration, web monitoring, and external workflow automation. The report deliberately focuses on this web-first operational architecture.

All implementation details and validation narratives are presented through the backend, web, and automation delivery tracks to maintain a consistent production-oriented scope.

\subsection{Target Audience}
The system targets three stakeholder groups with complementary goals:
\begin{itemize}
    \item \textbf{Administrators}: manage manager accounts and access governance.
    \item \textbf{Managers}: configure operational settings, monitor live queue status, react to alerts, and use indicators for staffing and service-quality planning.
    \item \textbf{End users}: benefit indirectly from reduced waiting times and smoother service flow.
\end{itemize}

This separation is important because each group consumes different levels of abstraction, from per-feed live events to aggregated performance trends.

\section{Project Management Methodology}

\subsection{Choice of Methodology: Agile}
An Agile approach was selected to deliver functional increments quickly while reducing integration risks early. The project combines multiple technical domains (computer vision, queue analytics, backend APIs, frontend workflows, and automation), each with uncertainties that are difficult to resolve using a single monolithic delivery cycle.

Iterative delivery made it possible to validate contracts progressively: first perception outputs, then analytical reliability, then API/runtime integration, then web usability, and finally workflow automation and hardening.

Development followed sprint-based Scrum planning with iterative validation. For report readability and implementation traceability, work is grouped into three logical modules.

\subsubsection{Module A: Backend Core (Sprints 1-3)}
This module established the vision and analytics backbone:
\begin{itemize}
    \item Sprint 1: detection, tracking, and zone filtering foundation,

\subsubsection{Module B: Web Experience (Sprints 4-5)}
This module focused on the web supervision experience:
\begin{itemize}
    \item Sprint 4: web design system and frontend scaffolding,
    \item Sprint 5: frontend integration with live backend metrics.
\end{itemize}

\subsubsection{Module C: Automation and Finalization (Sprints 6-8)}
This module covered integration hardening and closure:
\begin{itemize}
    \item Sprint 6: n8n automation and Telegram alerting,
    \item Sprint 7: evaluation and optimization,
    \item Sprint 8: report finalization and project consolidation.
