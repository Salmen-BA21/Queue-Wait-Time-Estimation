\section{Introduction}
Sprint 5 linked the dashboard to live backend services and runtime events. With the API client, websocket updates, and transport routing in place, the frontend could behave as an operational control panel instead of a static shell.

\section{Sprint Backlog}
Sprint 5 backlog covered integration-critical items:
\begin{itemize}
    \item implement a typed API client aligned with backend response contracts,
    \item integrate feed lifecycle actions (create/start/stop/restart/delete),
    \item integrate websocket events for low-latency dashboard updates,
    \item integrate capability-driven transport routing (WebRTC first, MJPEG fallback),
    \item implement resilient live monitoring behavior (reconnect and fallback),
    \item validate dashboard setup and onboarding workflows through integration tests.
\end{itemize}

Three primary sequences were implemented:
\begin{enumerate}
    \item \textbf{Feed lifecycle:} dashboard action $\rightarrow$ REST endpoint $\rightarrow$ registry update $\rightarrow$ websocket \texttt{feed\_status} event.
    \item \textbf{Live metrics:} worker metrics event $\rightarrow$ backend websocket $\rightarrow$ frontend cache merge $\rightarrow$ visual refresh.
    \item \textbf{Alert surfacing:} backend alert event $\rightarrow$ websocket \texttt{alert\_fired}/\texttt{system\_warning} $\rightarrow$ activity and attention views.
\end{enumerate}

\section{Implementation}
\subsection{Typed API Contract Integration}
The frontend contract is implemented in a dedicated TypeScript API client layer. It defines typed entities for feeds, metrics, alerts, and websocket events, and wraps network calls with explicit error classes (\texttt{ApiError}, \texttt{NetworkError}, \texttt{ValidationError}). This improved reliability of frontend-side error handling and debugging.

\subsection{Dashboard State Orchestration}
A dedicated dashboard state hook coordinates data fetching and mutations through React Query. Derived indicators (online feeds, total people, average wait time, attention counts) are computed from normalized feed state and exposed to dashboard widgets.

\subsection{WebSocket Reliability and Fallback Logic}
The websocket coordination hook implements:
\begin{itemize}
    \item reconnect backoff,
    \item heartbeat ping,
    \item stale-data watchdog,
    \item REST polling fallback during websocket degradation,
    \item batched metric flush to reduce UI re-render pressure.
\end{itemize}
When the connection drops, the dashboard falls back to REST polling instead of freezing, so operators still have a usable view during transient issues.

\subsection{Transport Capability Routing and WebRTC Lifecycle}
Live feed cards use capability-driven routing through the feed-grid component. For each running feed, the frontend queries \texttt{/api/feeds/\{feed\_id\}/transport}. If \texttt{webrtc.enabled=true}, \texttt{webrtc.ready=true}, and \texttt{source\_mode != none}, the dashboard selects WebRTC as the primary transport; otherwise it falls back to MJPEG.

The WebRTC lifecycle is implemented in a dedicated feed-connection hook using \texttt{RTCPeerConnection} \cite{webrtc_w3c}:
\begin{itemize}
    \item create connection with a receive-only video transceiver,
    \item gather ICE candidates (bounded wait before signaling),
    \item send browser SDP offer to \texttt{/api/feeds/\{feed\_id\}/webrtc/offer},
    \item apply backend SDP answer and switch feed card to live state.
\end{itemize}

Reconnection uses exponential backoff (1s, 2s, 5s, 10s). Retry is intentionally skipped for non-recoverable API statuses (404, 409, 422). Under those conditions, the transport layer degrades to MJPEG while preserving dashboard continuity.

When backend-annotated mode is active on WebRTC, client-side detection overlays are suppressed to avoid duplicate box rendering on top of server-rendered frames.

\subsection{Dashboard UI Integration}
The dashboard page integrates live feed controls, setup flow dialogs, source onboarding (RTSP/ONVIF/local file), KPI visualizations, and chart components. The page composes domain hooks and reusable dashboard components into one operational interface.

\subsection{Integration Testing}
Frontend integration behavior is validated with Vitest and Testing Library through scenario-based suites that cover dashboard setup flow execution, websocket-event handling, WebRTC lifecycle and fallback logic, feed-grid transport routing, and API error-contract behavior.

\section{Conclusion}
By the end of Sprint 5, the dashboard could react to live state, switch transport modes, and fall back cleanly when websocket or WebRTC paths failed. Sprint 6 then used that live surface for alert automation.
