\section{Introduction}
Sprint 1 built the full path from raw video to actionable queue indicators. It started by detecting people, tracking them across frames, and filtering observations to the queue zone. Once that perception baseline was reliable, the sprint moved to queue interpretation: estimating how fast people arrive, how quickly service handles them, and how long a new arrival should expect to wait.

This combination was deliberate. Perception without analytics produces only a count; analytics without stable perception produces unreliable rates. By delivering both in one sprint, the project established a trustworthy metric pipeline that every later sprint could consume directly.

\section{Sprint Objectives}
This sprint was focused on two complementary groups of outcomes:

\textbf{Perception objectives:}
\begin{itemize}
    \item detect people reliably in live and recorded video,
    \item preserve identity continuity across frames,
    \item filter detections to the configured queue zone,
    \item deliver a stable perception baseline for analytics.
\end{itemize}

\textbf{Analytics objectives:}
\begin{itemize}
    \item estimate arrival and service rates from tracked events,
    \item compute wait time in a way that remains meaningful during changing conditions,
    \item protect the runtime from empty or unstable windows,
    \item publish a metric contract that later layers can consume directly.
\end{itemize}

These objectives define the core of the system. If the perception layer is noisy or the analytics layer is fragile, every later metric and operational decision becomes harder to trust.

\section{Sprint Analysis}

\subsection{Runtime Scenarios}
Sprint 1 is best understood as a runtime pipeline that converts each frame into queue metrics. The scenarios below describe the conditions that the activity and sequence diagrams have to cover.

Four key scenarios are addressed in Sprint 1:
\begin{enumerate}
    \item \textbf{Person entry into queue zone:} when a person enters the queue area, the system treats that person as a possible arrival.
    \item \textbf{Consistency across frames:} when the same person appears in consecutive frames, the system keeps the identification stable and avoids double counting.
    \item \textbf{Zone filtering under mixed scenes:} people outside the queue area are ignored so the queue state stays focused on the relevant part of the scene.
    \item \textbf{Queue behavior under varying load:} when arrivals stay below service, the system uses the M/M/1 formula; when arrivals exceed service, the system switches to a conservative occupancy-based estimate without requiring an explicit stability output.
\end{enumerate}

\subsection{Operational Scenarios}
The queue analysis is easiest to understand through the situations it must handle every time a new metric window is evaluated:
\begin{enumerate}
    \item \textbf{Normal queue:} arrivals stay below service, so the M/M/1 formula gives a precise estimate based on measured rates.
    \item \textbf{Growing backlog:} arrivals start to approach service, so the system seamlessly switches to a conservative estimate based on current occupancy.
    \item \textbf{Empty or stalled queue:} no service events are available, so the output stays bounded and downstream logic receives safe, interpretable values.
\end{enumerate}
These scenarios explain why the sprint computes wait time with adaptive logic: a single metric that responds correctly to real-world queue conditions without requiring separate state signals.

\section{Implementation}

\subsection{Detection Layer}
The detection layer focuses on finding people in each frame while keeping the process adjustable for different machines. It is tuned to balance speed and accuracy, so the system stays responsive without losing the main detections that matter for the queue.

\subsection{Tracking Layer}
The tracking layer keeps the same person identifiable from one frame to the next. This is what makes arrival and departure counts more reliable than simply reading detections in a single frame \cite{bytetrack2022}.

\subsection{Zone-Aware Filtering}
Zone logic defines the queue area as a polygon on the frame and keeps only the people inside it. This avoids counting unrelated movement elsewhere in the scene and makes the measurement more relevant to the waiting line.

\subsection{Main Loop Integration}
The pipeline integration is handled in the runtime orchestration layer. The runtime supports:
\begin{itemize}
    \item handling local files, webcams, and live camera streams,
    \item adjusting how often frames are processed so the system stays responsive,
    \item showing detections, IDs, the queue zone, and metrics on screen,
    \item running without a visible interface when needed for later integration.
\end{itemize}

\subsection{Queue Event Windows and Rate Estimation}
The queue-analysis step uses short time windows to count arrivals and departures. Let $N_a$ and $N_d$ be the number of events observed in windows $T_a$ and $T_d$:
\[
\lambda = \frac{N_a}{T_a}, \qquad \mu = \frac{N_d}{T_d}
\]
From these counts, the system estimates the arrival rate and the service rate. To avoid unstable values at the beginning of a run, the implementation waits until enough events have been observed before returning non-zero rates.

\subsection{Wait-Time Logic and Adaptive Estimation}
The system estimates wait time using an adaptive formula that responds to queue conditions:
\[
W = \begin{cases}
\dfrac{1}{\mu - \lambda} & \text{if } \lambda < \mu \text{ and } \mu > 0 \\
\dfrac{L}{\mu} & \text{otherwise}
\end{cases}
\]
where $L$ is the current number of people in the zone. We use the M/M/1 sojourn-time expression because the project models each monitored lane as a single service channel with one effective queue, which matches the cashier-style setting studied in the report. This formula is also easy to interpret during a defense: it depends directly on the measured arrival and service rates, it gives a closed-form estimate without needing a large historical dataset, and it stays aligned with the real-time pipeline used by the tracker. Other models were less appropriate here: M/M/c would assume multiple parallel servers, which is not the default lane setup, and Little's Law is useful for validation but does not directly produce a forward wait-time estimate from the instantaneous rates alone.

The adaptive formula ensures the output always remains safe and interpretable: when arrivals are below service capacity, the formula is precise; when arrivals exceed capacity, it gracefully degrades to a conservative estimate based on current queue size. When no service events are observed, the implementation returns zero so that downstream components do not use an unreliable value.

\subsection{Runtime Metric Contract}
The final metric output includes:
\begin{itemize}
    \item point estimates ($\lambda$, $\mu$, $W$),
    \item people-in-zone occupancy.
\end{itemize}
These values are then reused by logs, overlays, webhook payloads, and dashboard events \cite{opencv_docs,gross_queueing}.

\section{Conclusion}
Sprint 1 delivered the full path from raw video to operational queue indicators. People can be detected, followed across frames, counted inside the queue area, and the resulting events are turned into arrival rates, service rates, and wait-time estimates. That gives the next sprint a trustworthy analytical contract to build on for camera integration and API services.

\section{Sprint Retrospective}
The main achievement of this sprint was connecting perception to interpretation in one delivery. The tracker and zone logic reduce false continuity problems, while the queue model provides an adaptive wait-time formula that remains interpretable across all operating conditions. A mathematically correct wait-time result is not enough if the input window is empty or the queue is overloaded, so the implementation had to treat safety and interpretability as equal concerns alongside detection accuracy.

The value of this sprint is that it gives the rest of the system a trustworthy metric layer. Once the queue state is expressed through rates and adaptive wait-time estimation, the dashboard and automation work can operate on structured signals instead of raw counts.
