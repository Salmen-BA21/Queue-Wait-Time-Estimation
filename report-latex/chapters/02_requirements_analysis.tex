\section{Introduction}
This chapter turns the project objective into the requirements that guided the implementation. We identify the actors, list the functions and quality constraints they need, and show how those requirements are spread across the implementation plan.

Rather than treating the requirements as an isolated checklist, we connect them to the queue-monitoring pipeline used throughout the project: video ingestion, person detection and tracking, queue-metric estimation, dashboard delivery, authentication, and alert automation. That link matters because the later chapters follow the same path from requirement to implementation, including the access layer used for manager onboarding and administrator governance.

\section{Requirements Specification}

\subsection{Identification of Actors}
The system has two actors whose responsibilities reflect the two main operating levels of the platform: governance and supervision. Both roles use the same application, but they do so with different permissions and goals.

The actors of the system are:
\begin{itemize}
    \item \textbf{Administrator}: manages manager accounts (create, update, delete) and controls access governance.
    \item \textbf{Manager}: configures sources and thresholds, monitors live queues, reacts to alerts, and reviews performance indicators.
\end{itemize}

This split makes the functional scope easier to explain and validate, because access-control flows and operational monitoring flows can be tested separately.

\subsection{Authentication and Access Governance}
The platform also includes a lightweight identity layer so that the dashboard is not open to anonymous use. Administrators authenticate to manage manager accounts, while managers can create an account, sign in, and continue their session through secure cookies. The backend supports session refresh, logout, password policy checks, account lockout after repeated failures, and audit logging. These controls matter because the monitoring and automation functions are tied to operational decisions and should not be exposed without clear access boundaries.

\subsection{Functional Requirements}
At a high level, the system captures a feed, counts people, estimates queue behavior, updates the dashboard, and sends alerts when needed. From that workflow, the system must provide the following capabilities:
\begin{itemize}
    \item real-time person detection and tracking,
    \item configurable queue zone definition,
    \item estimation of arrival rate ($\lambda$), service rate ($\mu$), and wait time ($W$),
    \item queue stability classification with robust wait-time fallback behavior,
    \item real-time web dashboard updates and alerts,
    \item RTSP and ONVIF camera integration,
    \item automated webhook and Telegram notifications,
    \item secure manager sign-up, sign-in, and role-based access control,
    \item historical data logging and analytics.
\end{itemize}

These requirements define the minimum end-to-end behavior expected from the platform. To keep the implementation trackable, we formalize them in a traceability matrix.

\subsection{Non-functional Requirements}
In addition to functional behavior, the platform must satisfy quality constraints that keep it usable in a live monitoring environment. Because the project combines computer vision, analytics, a web dashboard, and automation workflows, performance and reliability are as important as correctness. For this project, the main quality constraints are:
\begin{itemize}
    \item \textbf{Performance}: maintain real-time behavior and low alert latency.
    \item \textbf{Scalability}: support multiple feeds and independent feed lifecycle control.
    \item \textbf{Reliability}: tolerate transient source failures and integration interruptions.
    \item \textbf{Usability}: provide clear web workflows for monitoring and configuration.
    \item \textbf{Security}: protect integration channels and service endpoints.
    \item \textbf{Maintainability}: keep modular code organization and testable interfaces.
\end{itemize}

We treat these quality attributes as engineering contracts rather than only design intentions.

\section{Product Backlog}
The product backlog was prioritized according to business value and technical dependency. To keep the implementation easy to follow, we grouped the items into three domains that mirror the system architecture: backend processing, web supervision, and automation.
\begin{itemize}
    \item \textbf{Backend domain}: perception pipeline, queue analytics, API and stream interfaces.
    \item \textbf{Web domain}: dashboard UX, live monitoring integration, zone editing workflows.
    \item \textbf{Automation domain}: n8n workflow integration, alert routing, webhook reliability.
\end{itemize}

The first sprints focused on backend foundations, because the dashboard and automation layers depend on a stable metric contract. This order reduced integration risk and made later validation clearer.

\section{Data Modeling}
The data model combines runtime monitoring entities with persistence-oriented entities. Its role is to keep live telemetry, configuration data, and alert history aligned so that the system can support both immediate supervision and later analysis without the modules drifting apart.

\subsection{Core Entities}
The main objects are:
\begin{itemize}
    \item \textbf{VideoFeed}: source identity, connectivity, runtime status, and configuration.
    \item \textbf{FeedTransportCapabilities}: per-feed readiness flags for WebRTC and MJPEG routing.
    \item \textbf{QueueMetrics}: timestamped indicators (people in zone, $\lambda$, $\mu$, $W$, stability).
    \item \textbf{Alert}: severity, threshold context, and notification payload.
    \item \textbf{Establishment} and \textbf{Cashier}: business metadata used to organize feeds.
\end{itemize}

These entities mirror the runtime contract used by the backend so that live metrics, configuration data, and persisted records stay consistent across modules.

The authentication layer adds its own persistence objects for manager accounts, refresh sessions, and audit events.

\subsection{Data Lifecycle and Persistence Strategy}
Runtime metrics are generated continuously and distributed through live channels, while selected records are persisted for auditability and trend analysis. This dual-path strategy improves resilience because temporary integration failures do not imply complete data loss.

SQLite persistence stores operational metrics, structured metadata, authentication records, and alert archives in a single source of truth. That supports operational continuity as well as post-run diagnosis.

\subsection{Technologies Used}
The technology stack follows the main stages of the system:
\begin{itemize}
    \item \textbf{Vision pipeline}: YOLO26 (object detection model), ByteTrack (multi-object tracker), OpenCV (image processing and camera utilities) \cite{ultralytics_docs,bytetrack2022,opencv_docs}.
    \item \textbf{Queue analytics}: NumPy (numerical arrays), Pandas (table-oriented data), SciPy (statistical routines) and M/M/1 modeling (basic queueing theory) \cite{gross_queueing}.
    \item \textbf{Backend API}: FastAPI (chosen for its async support and automatic OpenAPI documentation generation) with Pydantic v2 (typed data validation and parsing).
    \item \textbf{Live transport}: WebRTC signaling via MediaMTX WHEP gateway (low-latency streaming) with MJPEG fallback (simple HTTP frame stream) \cite{webrtc_w3c,mediamtx_docs}.
    \item \textbf{Frontend}: React (component UI library), TypeScript (typed JavaScript), Vite (fast dev/build tool), Tailwind CSS (selected for rapid UI development with a consistent design system).
    \item \textbf{Automation}: n8n workflows (visual automation engine) with Telegram notifications (messaging alerts).
    \item \textbf{Persistence}: SQLite (lightweight relational database for metrics, metadata, and alert archival).
\end{itemize}

Each component was selected because it fits one layer of the system and keeps the implementation modular from perception through automation.

\subsection{Backend Architecture}
The backend exposes REST and websocket interfaces for feed lifecycle control and live metrics. It includes modules for detection orchestration, tracking, queue analysis, threshold evaluation, webhook delivery, and camera-source management.

Feed-level orchestration lets each camera be started, stopped, or refreshed independently. If one feed fails, the others keep running, and the dashboard still receives a predictable event stream.

We treat persistence and integration as core responsibilities rather than add-ons: SQLite-backed state preserves operational context, while webhook delivery turns queue events into external notifications.

\subsection{Frontend Architecture}
The frontend is built as a component-based interface with typed API integration, feed-oriented dashboard composition, and websocket-driven synchronization. Data access is isolated in hooks and client utilities, while pages and reusable components focus on presentation and interaction.

That separation keeps API changes localized to the integration layer and lets the visual components stay stable even when the backend contract changes. It also makes the dashboard easier to extend when new feed controls or indicators are added.
