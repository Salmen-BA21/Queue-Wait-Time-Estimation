\section{Introduction}
This chapter defines the project requirements and shows how those requirements shaped the architecture choices that follow. Instead of listing features in isolation, it ties the functional scope, actors, and layers back to the implementation plan used across the sprint chapters.

The chapter goes beyond a feature list. It sets out requirement traceability, actor responsibilities, quality constraints, sprint-scope mapping, core data entities, and the architecture layers used throughout the report.

\section{Requirements Specification}

\subsection{Identification of Actors}
The system involves two primary actors:
\begin{itemize}
    \item \textbf{Administrator}: manages manager accounts (create, update, delete) and controls access governance.
    \item \textbf{Manager}: configures sources and thresholds, monitors live queues, reacts to alerts, and reviews performance indicators.
\end{itemize}

Although these roles interact with the same platform, they consume different abstractions. Administrators require account-governance visibility, while managers require operational depth from setup through live supervision and KPI interpretation.

\end{table}

\subsection{Functional Requirements}
The system must provide the following core functionalities:
\begin{itemize}
    \item real-time person detection and tracking,
    \item configurable queue zone definition,
    \item estimation of arrival rate ($\lambda$), service rate ($\mu$), and wait time ($W$),
    \item queue stability classification with robust wait-time fallback behavior,
    \item real-time web dashboard updates and alerts,
    \item RTSP and ONVIF camera integration,
    \item automated webhook and Telegram notifications,
    \item historical data logging and analytics.
\end{itemize}

To support verification and sprint-level accountability, these requirements are formalized in a traceability matrix.

\subsection{Non-functional Requirements}
The main quality constraints are:
\begin{itemize}
    \item \textbf{Performance}: maintain real-time behavior and low alert latency.
    \item \textbf{Scalability}: support multiple feeds and independent feed lifecycle control.
    \item \textbf{Reliability}: tolerate transient source failures and integration interruptions.
    \item \textbf{Usability}: provide clear web workflows for monitoring and configuration.
    \item \textbf{Security}: protect integration channels and service endpoints.
    \item \textbf{Maintainability}: keep modular code organization and testable interfaces.
\end{itemize}

These quality attributes are treated as engineering contracts, not only design intentions.

\section{Product Backlog}
The product backlog was prioritized by business value and technical dependency. For implementation governance, backlog items were grouped into three domains:
\begin{itemize}
    \item \textbf{Backend domain}: perception pipeline, queue analytics, API and stream interfaces.
    \item \textbf{Web domain}: dashboard UX, live monitoring integration, zone editing workflows.
    \item \textbf{Automation domain}: n8n workflow integration, alert routing, webhook reliability.
\end{itemize}

Early execution emphasized backend foundations to reduce downstream integration risk. This sequencing ensured that web and automation layers consumed a stable metric contract rather than moving targets.

\section{Data Modeling}
The data model combines runtime monitoring entities and persistence entities. Its design objective is to support both low-latency supervision and post-hoc analysis with minimal contract drift across modules.

\subsection{Core Entities}
The main objects are:
\begin{itemize}
    \item \textbf{VideoFeed}: source identity, connectivity, runtime status, and configuration.
    \item \textbf{FeedTransportCapabilities}: per-feed readiness flags for WebRTC and MJPEG routing.
    \item \textbf{QueueMetrics}: timestamped indicators (people in zone, $\lambda$, $\mu$, $W$, stability).
    \item \textbf{Alert}: severity, threshold context, and notification payload.
    \item \textbf{Establishment} and \textbf{Cashier}: business metadata used to organize feeds.
\end{itemize}

\begin{table}[ht]
    \centering
    \caption{Conceptual entity mapping}
    \label{tab:conceptual_entity_mapping}
    \begin{tabularx}{\textwidth}{|l|X|X|}
        \hline
        Entity & Core semantics & Producer/consumer context \\ \hline
        VideoFeed & Declares source type, identity, status, and runtime control metadata. & Produced by onboarding/configuration flows; consumed by runtime and dashboard layers. \\ \hline
        FeedTransportCapabilities & Declares transport readiness (WebRTC and MJPEG), source mode, and unavailability reason for each feed. & Produced by API runtime transport endpoint; consumed by dashboard playback routing and fallback logic. \\ \hline
        QueueMetrics & Captures analytical outputs used for monitoring and decision support. & Produced by analysis loop; consumed by websocket/API/dashboard and alert logic. \\ \hline
        Alert & Encodes threshold breach context and notification-ready payload content. & Produced by threshold evaluation; consumed by webhook automation and archival paths. \\ \hline
        Establishment / Cashier & Binds feeds to business-level organization context. & Produced by metadata management APIs; consumed by setup and filtering interfaces. \\ \hline
    \end{tabularx}
\end{table}

\subsection{Data Lifecycle and Persistence Strategy}
Runtime metrics are generated continuously and distributed through live channels, while selected records are persisted for auditability and trend analysis. This dual-path strategy (stream plus persistence) improves resilience: temporary integration failures do not imply complete data loss.

SQLite database persistence stores operational metrics, structured metadata, and alert archives in one source of truth. This supports both operational continuity and post-run diagnosis.

\subsection{Technologies Used}
The selected technology stack is:
\begin{itemize}
    \item \textbf{Vision pipeline}: YOLO26, ByteTrack, OpenCV \cite{ultralytics_docs,bytetrack2022,opencv_docs}.
    \item \textbf{Queue analytics}: NumPy, Pandas, SciPy, M/M/1 modeling \cite{gross_queueing}.
    \item \textbf{Backend API}: FastAPI and Pydantic v2.
    \item \textbf{Live transport}: WebRTC signaling with MediaMTX WHEP gateway and MJPEG fallback \cite{webrtc_w3c,mediamtx_docs}.
    \item \textbf{Frontend}: React, TypeScript, Vite, Tailwind CSS.
    \item \textbf{Automation}: n8n workflows with Telegram notifications.
    \item \textbf{Persistence}: SQLite database for metrics, metadata, and alert archival.
\end{itemize}

The stack was chosen to keep each layer modular: every component needed a clear boundary, practical interoperability with the next layer, and enough flexibility to support live queue monitoring.

\section{Software Architecture}

\subsection{Overall Architecture}
The architecture is easier to read as four layers:
\begin{enumerate}
    \item \textbf{Video acquisition}: local files, RTSP streams, and ONVIF discovery.
    \item \textbf{Perception}: detection, tracking, and queue-zone filtering.
    \item \textbf{Analysis}: queue metrics estimation and stability handling.
    \item \textbf{Output and integration}: web dashboard, webhook dispatch, and alert automation.
\end{enumerate}

That separation keeps perception, analysis, UI, and automation independent enough to test on their own. For example, queue formulas depend on perception events, but do not depend on frontend rendering details.

    \centering
    \caption{Architecture layer-to-module mapping}
    \label{tab:architecture_layer_mapping}
    \begin{tabularx}{\textwidth}{|l|X|X|}

\subsection{Backend Architecture}
The backend exposes REST and websocket interfaces for feed lifecycle control and live metrics. It includes modules for detector orchestration, tracking, queue analysis, threshold detection, webhook delivery, and camera-source management.

Runtime orchestration focuses on feed-level lifecycle control and event broadcasting. That keeps feed state transitions independent and gives the dashboard and automation pipeline a clear event contract.

Persistence and integration are treated as part of the core system, not add-ons: SQLite-backed state and webhook reliability both belong to the operational architecture.

\subsection{Frontend Architecture}
The frontend is built as a component-based interface with typed API integration, feed-oriented dashboard composition, and websocket-driven synchronization. Data access lives in hooks and client utilities, while pages and reusable components handle presentation.

That split keeps API changes localized to the integration layer and leaves the visual components focused on rendering and interaction.
