\section{Introduction}
After defining the project context, the next step was to translate the idea into requirements that could guide the work. This chapter identifies the actors, lists the expected functions and quality constraints, and shows how those requirements are distributed across the implementation plan.

The requirements follow the same queue-monitoring path used throughout the project: video ingestion, person detection and tracking, queue-metric estimation, dashboard delivery, authentication, and alert automation.

\section{Requirements Specification}

\subsection{Identification of Actors}
The platform involves two actors inside the application and one operational actor outside it. This distinction matters because the software can detect, estimate, and notify, but the physical response to congestion still happens on site.

The actors are:
\begin{itemize}
    \item \textbf{Administrator}: manages manager accounts (create, update, delete) and controls access governance.
    \item \textbf{Manager}: configures sources and thresholds, monitors live queues, reacts to alerts, and reviews performance indicators.
    \item \textbf{On-site Operator (external actor)}: receives queue alert notifications in a shared Telegram group and applies field actions, such as opening a new queue line or redirecting customer flow.
\end{itemize}

This split keeps the functional scope clear: access control, monitoring, and alert notification remain inside the system, while physical queue intervention and manual completion confirmation are treated as external operational actions.

\section{Product Backlog and Sprint Organization}
The product backlog was prioritized according to business value and technical dependency, then organized into four sprints. The first sprint focused on perception and queue analytics because the dashboard and alerts depend on stable metrics. The second sprint added source management and live services. The third sprint turned those services into a usable web dashboard. The final sprint connected alerts to n8n and Telegram, then evaluated the complete system.

\subsection{Product Backlog}
The product backlog groups the global functionalities of the application into user stories. These stories are prioritized with the MoSCoW method:
\begin{itemize}
    \item \textbf{M -- Must have}: essential requirements without which the project would not meet its objective.
    \item \textbf{S -- Should have}: important requirements that improve the solution but are not blocking for the core system.
    \item \textbf{C -- Could have}: desirable enhancements that add comfort or completeness when time permits.
    \item \textbf{W -- Would have}: requirements deliberately left outside the current scope and reserved for future improvement.
\end{itemize}

\subsection{Technologies Used}
The technology stack follows the main stages of the system, from video perception through to automation and persistence. Each technology is described below.

\textbf{YOLO26} \cite{ultralytics_docs} is a real-time object detection model that processes entire images in a single forward pass through a convolutional neural network. In this project, it serves as the perception backbone, detecting people in video frames with high speed and accuracy.

\textbf{ByteTrack} \cite{bytetrack2022} is a multi-object tracking algorithm that associates detections across frames using both high- and low-confidence bounding boxes, reducing identity switches. It is used here to maintain persistent person identities throughout the video stream, which is essential for accurate queue measurement.

\textbf{OpenCV} \cite{opencv_docs} is an open-source computer vision library providing tools for image processing, video capture, and graphical annotation. It handles frame acquisition from cameras and uploaded videos, and renders visual overlays such as bounding boxes and zone boundaries.

\textbf{FastAPI} \cite{fastapi_docs} is a modern Python web framework designed for building high-performance HTTP and WebSocket APIs with automatic data validation and interactive documentation. It exposes the system's endpoints and coordinates communication between the vision pipeline, analytics engine, and frontend.

\textbf{Pydantic v2} \cite{pydantic_docs} is a data validation library that enforces strict typing on request and response models at runtime. It is used alongside FastAPI to ensure that all data exchanged between system components conforms to defined schemas.

\textbf{React} \cite{react_docs} is a JavaScript library for building component-based user interfaces. Combined with TypeScript \cite{typescript_docs} for static typing, Vite \cite{vite_docs} as the build toolchain, and Tailwind CSS \cite{tailwind_docs} for utility-based styling, it forms the foundation of the monitoring dashboard.

\textbf{WebRTC} \cite{webrtc_w3c} is a browser standard enabling low-latency audio and video streaming directly in the browser without plugins. It is used to deliver live camera feeds to the dashboard, while MediaMTX \cite{mediamtx_docs} acts as the WHEP gateway bridging the camera source to the browser, with MJPEG serving as a simpler fallback for uploaded video files.

\textbf{n8n} \cite{n8n_docs} is an open-source workflow automation platform that connects services through configurable pipelines. It routes queue alerts generated by the backend and delivers them as operational messages via the Telegram Bot API \cite{telegram_bot_api}.

\textbf{SQLite} \cite{sqlite_docs} is a lightweight embedded relational database that requires no separate server process. It stores queue metrics, session metadata, and alert history locally alongside the application for later analysis.

\textbf{NumPy}, \textbf{Pandas}, and \textbf{SciPy} \cite{numpy_docs,pandas_docs,scipy_docs} are foundational Python scientific computing libraries used in the analytics pipeline. NumPy supports numerical array operations, Pandas handles structured metric storage and manipulation, and SciPy provides statistical routines. Wait-time estimation is derived from an M/M/1 queuing model \cite{gross_queueing}, which approximates queue behavior under Poisson arrivals and exponential service times.

This selection supports the complete path from perception through automation while keeping each stage understandable on its own.
\section{Software Architecture}

\subsection{Overall Architecture}
The architecture is organized into four stages that match the flow of data through the system, from input acquisition to output delivery. Figure~\ref{fig:overall_architecture} illustrates this flow.
\begin{figure}[!htbp]
    \centering
    \includegraphics[width=0.95\textwidth]{\detokenize{chapter2_architecture.pdf}}
    \caption{Overall system architecture from video acquisition to alert delivery.}
    \label{fig:overall_architecture}
\end{figure}

\begin{enumerate}
    \item \textbf{Input acquisition}: multiple sources feed into the acquisition component, which handles connection management and stream ingestion.
    \item \textbf{Processing}: the processing engine applies algorithms to extract structured observations from raw input data and exposes them through a defined interface.
    \item \textbf{Analysis}: the analysis module receives structured observations and computes quantitative metrics using domain-specific models and evaluation logic.
    \item \textbf{Output and integration}: the backend acts as the distribution hub that routes computed metrics across three outputs: the live interface via real-time channels, the persistence layer for historical records, and the orchestrator which forwards events to external notification services.
\end{enumerate}

This separation keeps the four stages easier to validate. Analysis formulas depend on processing outputs, the backend depends on the metric contract, and the interface, persistence, and orchestration consume the same outputs without being tightly coupled to one another.

\subsection{Backend Architecture}
The backend adopts a three-tier layered architecture combined with a Backend-for-Frontend (BFF) pattern. The layered architecture organizes the system vertically into separate tiers based on responsibility, while the BFF pattern tailors the backend API specifically to the requirements of the frontend client, rather than serving as a generic intermediary.

It is composed of three main layers:
\begin{itemize}
    \item \textbf{Presentation layer}: serves as the entry point, exposing HTTP endpoints and real-time communication channels that receive client requests, validate input data, and return structured responses suitable for direct consumption by the user interface.
    \item \textbf{Application layer}: contains the orchestration and business logic. It coordinates operations, enforces rules, manages workflows, evaluates conditions, and broadcasts events across the system.
    \item \textbf{Data and integration layer}: handles persistence and external service communication. It manages data storage operations and abstracts the details of third-party service interactions through dedicated integration adapters.
\end{itemize}

The three-tier layered architecture offers several benefits such as:
\begin{itemize}
    \item \textbf{Separation of concerns}: each layer has a single responsibility, making the system easier to understand and maintain.
    \item \textbf{Improved testability}: layers can be tested independently by mocking dependencies between them.
    \item \textbf{Flexibility}: changes in one layer have minimal impact on the others, allowing independent evolution of persistence, business logic, and API contracts.
\end{itemize}

The Backend-for-Frontend pattern further enhances this architecture by shaping the presentation layer around the specific needs of the dashboard interface. This approach groups related operations together, reduces the number of client requests, and delivers aggregated responses optimized for the frontend use cases, ultimately simplifying the client-side logic.
\subsection{Frontend Architecture}
The frontend adopts the Model-View-ViewModel (MVVM) architectural pattern, an evolution of the classical Model-View-Controller (MVC) pattern in which the Controller is replaced by a dedicated ViewModel component. The ViewModel acts as a bridge between the Model and the View, facilitating data binding and separating presentation logic from the user interface. It is composed of:

\begin{itemize}
    \item \textbf{Model}: represents the data and business logic of the application. It defines the data structures, service contracts, and the way the application interacts with backend services and external data sources.
    \item \textbf{View}: represents the application's user interface. It is responsible for displaying information to the user and capturing user interactions through visual components and layouts.
    \item \textbf{ViewModel}: acts as the intermediary between the Model and the View. On one hand, it transforms and prepares data for presentation and updates the View through data binding mechanisms. On the other hand, it processes user interactions captured by the View and updates the Model accordingly.
\end{itemize}

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=0.85\textwidth]{\detokenize{MVVMDesign.png}}
    \caption{MVVM architectural pattern showing the relationship between Model, View, and ViewModel components.}
    \label{fig:mvvm_design}
\end{figure}

The MVVM design pattern was chosen for its advantages such as:
\begin{itemize}
    \item \textbf{Improved testability}: ViewModels can be tested independently of the View, enabling unit testing of presentation logic without UI dependencies.
    \item \textbf{Separation of concerns}: the pattern clearly distinguishes between data management, business logic, and user interface presentation, making the codebase easier to maintain and evolve.
    \item \textbf{Data binding support}: the ViewModel facilitates automatic synchronization between the View and the Model, reducing boilerplate code and improving consistency.
\end{itemize}
