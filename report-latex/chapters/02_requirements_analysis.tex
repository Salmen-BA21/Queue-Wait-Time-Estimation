\section{Introduction}
After defining the project context, the next step was to translate the idea into requirements that could guide the work. This chapter identifies the actors, lists the expected functions and quality constraints, and shows how those requirements are distributed across the implementation plan.

The requirements follow the same queue-monitoring path used throughout the project: video ingestion, person detection and tracking, queue-metric estimation, dashboard delivery, authentication, and alert automation.

\section{Requirements Specification}

\subsection{Identification of Actors}
The platform involves two actors inside the application and one operational actor outside it. This distinction matters because the software can detect, estimate, and notify, but the physical response to congestion still happens on site.

The actors are:
\begin{itemize}
    \item \textbf{Administrator}: manages manager accounts (create, update, delete) and controls access governance.
    \item \textbf{Manager}: configures sources and thresholds, monitors live queues, reacts to alerts, and reviews performance indicators.
    \item \textbf{On-site Operator (external actor)}: receives queue alert notifications in a shared Telegram group and applies field actions, such as opening a new queue line or redirecting customer flow. In the MVP, the operator confirms completion manually in Telegram, and this confirmation is not automatically captured by the application.
\end{itemize}

This split keeps the functional scope clear: access control, monitoring, and alert notification remain inside the system, while physical queue intervention and manual completion confirmation are treated as external operational actions.

\section{Product Backlog and Sprint Organization}
The product backlog was prioritized according to business value and technical dependency, then organized into four sprints. The first sprint focused on perception and queue analytics because the dashboard and alerts depend on stable metrics. The second sprint added source management and live services. The third sprint turned those services into a usable web dashboard. The final sprint connected alerts to n8n and Telegram, then evaluated the complete system.

\section{Software Architecture}

\subsection{Overall Architecture}
The architecture is described as four stages that match the flow of data through the system, from video acquisition to alert delivery. Figure~\ref{fig:overall_architecture} illustrates this flow.
\begin{figure}[!htbp]
    \centering
    \includegraphics[width=0.95\textwidth]{\detokenize{chapter2_architecture.pdf}}
    \caption{Overall system architecture from video acquisition to alert delivery.}
    \label{fig:overall_architecture}
\end{figure}

\begin{enumerate}
    \item \textbf{Video acquisition}: camera sources and video streams (RTSP, ONVIF, and local files) feed into the video acquisition component, which handles frame capture and stream management \cite{rtsp_rfc2326,onvif_specs}.
    \item \textbf{Perception}: the perception engine runs detection and tracking on each captured frame and exposes tracked identities through a defined interface to the queue analyzer.
    \item \textbf{Analysis}: the queue analyzer receives tracked events and computes queue metrics ($\lambda$, $\mu$, $W$) using adaptive wait-time estimation logic.
    \item \textbf{Output and integration}: the backend API acts as the hub that receives queue metrics and distributes them across three outputs: the live dashboard via a real-time feed, the persistence layer (SQLite) for historical records, and the alert orchestrator (n8n) which routes alert payloads to the Telegram notification channel.
\end{enumerate}

This separation keeps the four stages easier to validate. Queue formulas depend on perception events, the API depends on the metric contract, and the dashboard, persistence, and alert orchestration consume the same project-level outputs without being tightly coupled to one another.

\subsection{Backend Architecture}
The backend exposes REST and WebSocket interfaces for feed lifecycle control and live metrics. It coordinates the main project responsibilities: source management, queue analysis, threshold evaluation, alert delivery, and live dashboard updates.

Feed-level orchestration lets each camera be started, stopped, or refreshed independently. If one feed fails, the others keep running, and the dashboard still receives a predictable event stream.

Persistence and integration are treated as core responsibilities rather than add-ons. Stored state preserves operational context, while webhook delivery turns queue events into external notifications.

\subsection{Frontend Architecture}
The frontend is built as a component-based interface with feed-oriented dashboard composition and WebSocket-driven synchronization. Its role is to make setup, monitoring, and analytics usable for managers without exposing the complexity of the underlying services.

This separation makes the dashboard easier to extend when new feed controls or indicators are added, while preserving a stable user experience for monitoring and setup.
