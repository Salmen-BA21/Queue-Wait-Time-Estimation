\section{Introduction}
This chapter turns the project objective into the requirements that guided the implementation. It identifies the actors, lists the functions and quality constraints they need, and shows how those requirements are spread across the implementation plan.

The requirements are tied to the queue-monitoring pipeline used throughout the project: video ingestion, person detection and tracking, queue-metric estimation, dashboard delivery, authentication, and alert automation. This connection matters because the later chapters follow the same path from requirement to implementation, including the access layer used for manager onboarding and administrator governance.

\section{Requirements Specification}

\subsection{Identification of Actors}
The system has two actors whose responsibilities reflect the two main operating levels of the platform: governance and supervision. Both roles use the same application, but they do so with different permissions and goals.

The actors of the system are:
\begin{itemize}
    \item \textbf{Administrator}: manages manager accounts (create, update, delete) and controls access governance.
    \item \textbf{Manager}: configures sources and thresholds, monitors live queues, reacts to alerts, and reviews performance indicators.
\end{itemize}

This split makes the functional scope easier to explain and validate, because access-control flows and operational monitoring flows can be tested separately.

\subsection{Functional Requirements}
At a high level, the system captures a feed, counts people, estimates queue behavior, updates the dashboard, and sends alerts when needed. From that workflow, the system must provide the following capabilities:
\begin{itemize}
    \item real-time person detection and tracking,
    \item configurable queue zone definition,
    \item estimation of arrival rate ($\lambda$), service rate ($\mu$), and wait time ($W$),
    \item queue stability classification with robust wait-time fallback behavior,
    \item real-time web dashboard updates and alerts,
    \item IP camera integration through complementary ONVIF discovery and RTSP streaming,
    \item automated webhook and Telegram notifications,
    \item secure manager sign-up, sign-in, and role-based access control,
    \item historical data logging and analytics.
\end{itemize}

\subsection{Non-functional Requirements}
In addition to functional behavior, the platform must satisfy quality constraints that keep it usable in a live monitoring environment. Because the project combines computer vision, analytics, a web dashboard, and automation workflows, performance and reliability matter as much as correctness. For this project, the main quality constraints are:
\begin{itemize}
    \item \textbf{Performance}: maintain real-time behavior and low alert latency.
    \item \textbf{Scalability}: support multiple feeds and independent feed lifecycle control.
    \item \textbf{Reliability}: tolerate transient source failures and integration interruptions.
    \item \textbf{Usability}: provide clear web workflows for monitoring and configuration.
    \item \textbf{Security}: protect integration channels and service endpoints.
    \item \textbf{Maintainability}: keep modular code organization and testable interfaces.
\end{itemize}

\section{Product Backlog}
The product backlog was prioritized according to business value and technical dependency. To keep the implementation easy to follow, the items were grouped into three domains that mirror the system architecture: backend processing, web supervision, and automation.
\begin{itemize}
    \item \textbf{Backend domain}: perception pipeline, queue analytics, API and stream interfaces.
    \item \textbf{Web domain}: dashboard UX, live monitoring integration, zone editing workflows.
    \item \textbf{Automation domain}: n8n workflow integration, alert routing, webhook reliability.
\end{itemize}

The first sprints focused on backend foundations, because the dashboard and automation layers depend on a stable metric contract. This order reduced integration risk and made later validation clearer.

\section{Software Architecture}

\subsection{Overall Architecture}
The architecture is described as four stages that match the flow of data through the system, from video acquisition to alert delivery, as illustrated in Figure~\ref{fig:overall_architecture}.
\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{\detokenize{chapter2_architecture.pdf}}
    \caption{Overall system architecture from video acquisition to alert delivery.}
    \label{fig:overall_architecture}
\end{figure}

\begin{enumerate}
    \item \textbf{Video acquisition}: local files, RTSP streams, and ONVIF discovery \cite{rtsp_rfc2326,onvif_specs}.
    \item \textbf{Perception}: detection, tracking, and queue-zone filtering.
    \item \textbf{Analysis}: queue metrics estimation and stability handling.
    \item \textbf{Output and integration}: web dashboard, webhook dispatch, and alert automation.
\end{enumerate}

This separation keeps perception, analysis, the user interface, and automation independently testable. For example, queue formulas depend on perception events, but they do not depend on the frontend or notification delivery.

\subsection{Backend Architecture}
The backend exposes REST and websocket interfaces for feed lifecycle control and live metrics. It includes modules for detection orchestration, tracking, queue analysis, threshold evaluation, webhook delivery, and camera-source management.

Feed-level orchestration lets each camera be started, stopped, or refreshed independently. If one feed fails, the others keep running, and the dashboard still receives a predictable event stream.

We treat persistence and integration as core responsibilities rather than add-ons: a durable backend state store preserves operational context, while webhook delivery turns queue events into external notifications.

\subsection{Frontend Architecture}
The frontend is built as a component-based interface with typed API integration, feed-oriented dashboard composition, and websocket-driven synchronization. Data access is isolated in hooks and client utilities, while pages and reusable components focus on presentation and interaction.

That separation keeps API changes localized to the integration layer and lets the visual components stay stable even when the backend contract changes. It also makes the dashboard easier to extend when new feed controls or indicators are added.
