\section{Introduction}
This chapter formalizes the requirement baseline that guided implementation choices across backend perception, queue analytics, web supervision, and automation workflows. Its role is twofold: define what the system must provide, and justify how architectural decomposition supports those requirements.

The chapter therefore goes beyond feature listing. It introduces requirement traceability, actor responsibilities, quality constraints, sprint-scope mapping, conceptual data entities, and software architecture layers. These elements are used as reference contracts for the sprint implementation chapters.

\section{Requirements Specification}

\subsection{Identification of Actors}
The system involves three primary actors:
\begin{itemize}
    \item \textbf{Administrator}: configures sources, thresholds, and integration parameters.
    \item \textbf{Operator}: monitors live queues and reacts to alerts during operations.
    \item \textbf{Manager}: analyzes historical trends and uses indicators for planning decisions.
\end{itemize}

Although these roles interact with the same platform, they consume different abstractions. Administrators require configuration and diagnostics depth, operators require low-latency situational awareness, and managers require interpretable KPI summaries for decision support.

\subsection{Functional Requirements}
The system must provide the following core functionalities:
\begin{itemize}
    \item real-time person detection and tracking,
    \item configurable queue zone definition,
    \item estimation of arrival rate ($\lambda$), service rate ($\mu$), and wait time ($W$),
    \item uncertainty quantification for queue metrics,
    \item real-time web dashboard updates and alerts,
    \item RTSP and ONVIF camera integration,
    \item automated webhook and Telegram notifications,
    \item historical data logging and analytics.
\end{itemize}

\subsection{Non-functional Requirements}
The main quality constraints are:
\begin{itemize}
    \item \textbf{Performance}: maintain real-time behavior and low alert latency.
    \item \textbf{Scalability}: support multiple feeds and independent feed lifecycle control.
    \item \textbf{Reliability}: tolerate transient source failures and integration interruptions.
    \item \textbf{Usability}: provide clear web workflows for monitoring and configuration.
    \item \textbf{Security}: protect integration channels and service endpoints.
    \item \textbf{Maintainability}: keep modular code organization and testable interfaces.
\end{itemize}

These quality attributes are treated as engineering contracts, not only design intentions.

\section{Product Backlog}
The product backlog was prioritized by business value and technical dependency. For implementation governance, backlog items were grouped into three domains:
\begin{itemize}
    \item \textbf{Backend domain}: perception pipeline, queue analytics, API and stream interfaces.

    \item \textbf{Automation domain}: n8n workflow integration, alert routing, webhook reliability.

Early execution emphasized backend foundations to reduce downstream integration risk. This sequencing ensured that web and automation layers consumed a stable metric contract rather than moving targets.

\section{Data Modeling}
The data model combines runtime monitoring entities and persistence entities. Its design objective is to support both low-latency supervision and post-hoc analysis with minimal contract drift across modules.

\subsection{Core Entities}
The main objects are:
\begin{itemize}
    \item \textbf{VideoFeed}: source identity, connectivity, runtime status, and configuration.
    \item \textbf{QueueMetrics}: timestamped indicators (people in zone, $\lambda$, $\mu$, $W$, stability).
    \item \textbf{Alert}: severity, threshold context, and notification payload.
    \item \textbf{Establishment} and \textbf{Caisse}: business metadata used to organize feeds.
\end{itemize}

\begin{table}[ht]
    \centering
    \caption{Conceptual entity mapping}
    \label{tab:conceptual_entity_mapping}
    \begin{tabularx}{\textwidth}{|l|X|X|}
        \hline
        Entity & Core semantics & Producer/consumer context \\ \hline
        VideoFeed & Declares source type, identity, status, and runtime control metadata. & Produced by onboarding/configuration flows; consumed by runtime and dashboard layers. \\ \hline
        QueueMetrics & Captures analytical outputs used for monitoring and decision support. & Produced by analysis loop; consumed by websocket/API/dashboard and alert logic. \\ \hline
        Alert & Encodes threshold breach context and notification-ready payload content. & Produced by threshold evaluation; consumed by webhook automation and archival paths. \\ \hline
        Establishment / Caisse & Binds feeds to business-level organization context. & Produced by metadata management APIs; consumed by setup and filtering interfaces. \\ \hline
    \end{tabularx}
\end{table}

\subsection{Data Lifecycle and Persistence Strategy}
Runtime metrics are generated continuously and distributed through live channels, while selected records are persisted for auditability and trend analysis. This dual-path strategy (stream plus persistence) improves resilience: temporary integration failures do not imply complete data loss.

CSV logging supports rapid observability and portability, while SQLite supports structured metadata and alert archival. Together, these storage paths enable both operational continuity and post-run diagnosis.

\end{itemize}

Technology selection follows a modular criterion: each component must provide clear contract boundaries and practical interoperability with adjacent layers.

\section{Software Architecture}

\subsection{Overall Architecture}
The system architecture is organized in four layers:
\begin{enumerate}
    \item \textbf{Video acquisition}: local files, RTSP streams, and ONVIF discovery.
    \item \textbf{Perception}: detection, tracking, and queue-zone filtering.
    \item \textbf{Analysis}: queue metrics estimation and uncertainty modeling.
    \item \textbf{Output and integration}: web dashboard, webhook dispatch, and alert automation.
\end{enumerate}

This layering constrains coupling and simplifies testing. For example, queue formulas depend on perception events, but do not depend on frontend rendering details.

\begin{table}[ht]
    \centering
    \caption{Architecture layer-to-module mapping}
    \label{tab:architecture_layer_mapping}
    \begin{tabularx}{\textwidth}{|l|X|X|}

        Output/integration & API/websocket exposure, webhook dispatch, persistence, dashboard consumption. & \texttt{api/app.py}, \texttt{api/runtime.py}, \texttt{webhook\_client.py}, frontend hooks/pages \\ \hline

\end{table}

\subsection{Backend Architecture}
The backend exposes REST and websocket interfaces for feed lifecycle control and live metrics. It includes modules for detector orchestration, tracking, queue analysis, threshold detection, webhook delivery, and camera-source management.

Runtime orchestration is centered around feed-level lifecycle control and event broadcasting. This design supports independent feed state transitions and clear event contracts consumed by the dashboard and automation pipeline.

Persistence and integration are treated as first-class concerns: CSV metrics logging, SQLite metadata state, and webhook dispatch reliability are all part of the operational architecture rather than optional add-ons.

\subsection{Frontend Architecture}
The frontend follows a component-based architecture with typed API contract mapping, feed-oriented dashboard composition, and websocket-driven synchronization. It separates data-access concerns (API client and hooks) from presentation concerns (pages and reusable components).

This separation improves maintainability: backend contract adjustments can be localized to integration hooks and API utilities, while visual components remain focused on rendering and interaction logic.
